# GitHub 공개 전 보안·개인정보 검토

검토일: 2026-10-28. 대상: 교실 서랍 정적 허브와 신규 Firebase 일기장. 기존 로컬 일기 데이터는 검토·복사·업로드하지 않았습니다.

## 공개 범위

- 공개 저장소: 정적 UI, Firebase 클라이언트 코드, 보안 규칙, 테스트, 빌드 스크립트, 사용 안내.
- GitHub Pages: 빌드 스크립트가 허용한 정적 파일만 `gh-pages` 브랜치로 게시. Sites 내부 메타데이터, 로컬 서버, 테스트와 개발 도구는 웹 배포 파일에 포함하지 않음.
- 제외: SQLite 파일, 개인 일기 내용, CLI 로그인 상태·토큰·개인 키·서비스 계정, 디버그 로그, Sites 메타데이터, 컴퓨터의 절대 경로.
- Firebase 웹 설정의 `apiKey`, `authDomain`, `projectId`, `appId`는 브라우저용 공개 설정입니다. 서버 관리 키가 아니며, 데이터 접근은 Firebase Auth와 Firestore 규칙으로 제한합니다.

## 확인 및 보강

1. 사용자 입력은 DOM textContent 또는 HTML 이스케이프로 표시합니다. 추가 링크는 HTTPS/명시적 루프백만 허용하고 실행 가능한 URL, URL 내 계정 정보, 토큰·API 키·이메일·학번 등 민감한 쿼리를 차단합니다. 모든 개인정보를 자동 식별하는 기능은 아니므로 민감한 링크는 등록하면 안 됩니다.
2. 허브에는 외부 분석·추적 스크립트가 없습니다. CSP와 referrer 정책을 추가했습니다. Firebase 로그인에 필요한 Google 리소스는 일기장 페이지에만 허용합니다.
3. 일기는 `users/{Firebase UID}/entries/{entryId}` 경로에 저장합니다. 익명·다른 사용자 접근과 전체 사용자 조회를 차단했습니다. 프로필·역할·관리자 권한을 사용자가 추가할 수 없습니다.
4. 생성과 수정 모두 필수 필드, 허용 필드, 자료형, 실제 날짜, 제목 200자·본문 100,000자 제한, 기분 값, 서버 시각을 검증합니다. 생성 시각은 변경할 수 없습니다.
5. 로그인 상태는 탭 세션에만 유지하고 Firestore 영구 오프라인 저장을 사용하지 않습니다. 로그아웃·계정 변경 시 화면을 비우고 기존 비동기 응답을 무시합니다. 네트워크 장애로 삭제가 대기해도 로그아웃을 막지 않도록 독립 코드 검토 후 수정했습니다.
6. 저장 성공은 서버 응답 이후에만 표시합니다. 새 일기의 실패 재시도는 같은 문서 ID를 사용해 중복 생성을 줄입니다. 검색어와 일기 본문을 URL·분석 도구·콘솔 로그에 쓰지 않습니다.
7. Firebase 관련 의존성의 gRPC 경고를 수정된 1.x 호환 버전으로 보강했습니다. 설치 스크립트를 비활성화하고 lockfile을 고정했습니다. 최종 npm audit 결과: 발견된 취약점 0개.

## 검증 증거

- 일반 단위 테스트 11개 통과: 타이머, URL 검증, 입력 검증, 사용자별 경로, 검색, 로그아웃 및 계정 전환 후 늦은 응답 차단.
- 실제 Firestore 에뮬레이터 테스트 7개 통과: 본인 CRUD·목록, 익명 및 다른 사용자 접근 차단, 필수 필드·타입·크기·역할·생성시각 수정 차단, 무제한 목록과 컬렉션 그룹 조회 차단, 윤년·줄바꿈 본문.
- 별도 코드 검토에서 발견된 로그아웃 차단 문제 수정 후 단위 테스트 재실행 및 수정 검토 완료.
- Firebase 실환경: 서울 리전 `asia-northeast3`, Standard, 무료 할당량 대상 데이터베이스 생성 확인. 규칙 배포 및 Google 인증 설정 배포 성공.
- GitHub Pages 배포 성공과 허브·일기장·주요 정적 자산의 HTTP 200을 확인했습니다. 서버가 제공하는 7개 핵심 파일이 검토한 배포 파일과 바이트 단위로 일치합니다.
- Firebase 실환경의 로그인 없는 문서 조회가 `403 PERMISSION_DENIED`로 차단되고 Google OAuth 시작 URL 생성이 성공하는 것을 확인했습니다.
- 실제 팝업 검사에서 발견된 `auth/unauthorized-domain`의 원인은 CLI 15.34.1이 제공자 설정만 배포하고 허용 도메인 필드를 무시하는 점이었습니다. 관리자 설정의 기존 도메인을 보존하면서 GitHub Pages 호스트를 추가했고, 서버 조회로 반영을 검증했습니다.
- 도메인 수정 후 사용자가 Google 로그인 완료 및 일기 작성 화면 진입을 직접 확인했습니다. 실제 계정으로 일기 저장까지의 검증은 수행하지 않았으며, CRUD·데이터 검증·사용자 간 차단은 에뮬레이터에서 확인했습니다.

## 처리 방식과 한계

Google 계정 식별 정보는 Firebase Authentication에서 처리하며 이름·이메일을 일기 문서에 복사하지 않습니다. 일기 날짜·제목·본문·기분·시각은 Google Firestore에 저장합니다. 프로젝트 관리 권한이 있는 운영자는 Firebase 관리 도구로 데이터에 접근할 수 있습니다. 종단간 암호화는 구현하지 않았습니다.

직접 삭제할 때까지 보관하며 화면에서 개별 삭제와 현재 불러온 일기의 JSON 내려받기를 제공합니다. 계정 및 전체 데이터 삭제는 프로젝트 운영자가 Authentication 계정과 하위 일기 문서를 모두 삭제해야 합니다. Authentication 계정만 삭제해도 하위 문서가 자동 삭제되지는 않습니다. 내려받은 파일의 관리와 기기 백업은 사용자 책임입니다.

기존 외부 학습 앱은 공개 소개·게시 상태를 바탕으로 링크를 등록했으며, 각 서비스 전체를 보안 감사한 것은 아닙니다. 학생 개인정보·민감한 제3자 자료를 기록하는 학교 업무 시스템으로 검증한 것도 아닙니다. 과금 계정을 연결하지 않았으며 할당량이 소진되면 읽기·쓰기가 제한될 수 있습니다.

I've set up prototype Security Rules to keep the data in Firestore safe. They are designed to be secure for a private diary because every document is scoped to the authenticated owner and creates and updates validate the complete schema. However, you should review and verify them before broadly sharing your app. If you'd like, I can help you harden these rules.

보안 규칙은 위 검증을 수행한 초기 규칙이며, 모든 취약점이 없다는 보장은 아닙니다. 학교 전체 등 광범위하게 공유하기 전에는 운영 조건과 권한 정책을 추가 검토해야 합니다.
